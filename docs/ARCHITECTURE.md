# EvidenceGate 系统架构

> 这份文档回答一个问题：**这个系统由哪几块组成，每块为什么存在，块与块之间的边界在哪。**
> 想知道"某个具体函数干什么"，看 `MODULES.md`；想知道"为什么这样设计"，看本文。

---

## 1. 一句话定位

EvidenceGate 是一个**领域无关的证据链裁定系统**：

> 把一堆材料变成"可核验的主张"，再用一套**不允许互相抵消**的闸门判出结论，
> 最后产出一个离线也能复核的证据包。

它不知道自己在审什么。报销、人才筛选、合同审查，对它来说都只是换了
一个 **profile**（场景配置）。这是整个架构的核心决定，下面所有分层都服务于它。

---

## 2. 为什么要分层

如果不分层，代码会退化成这样：业务规则里混着数据库读写，数据库读写里混着
调用模型，模型输出直接决定最终结论。后果不是"代码难看"，而是三个具体的问题：

| 问题 | 后果 |
| --- | --- |
| 结论不可复现 | 同一个案件跑两次得出不同结论，没人能解释差异来自哪 |
| 结论不可追责 | 说不出这条结论依据了哪几行原文、由谁签的字 |
| 规则可被抵消 | 材料不全扣一点分、引用缺失扣一点分，最后还得了个"合格" |

分层的目的是让**结论的产生过程变成一个纯函数**：

```
(材料, 主张, 发现, 签署)  →  结论
```

同样的输入永远得到同样的输出，不读数据库、不看时钟、不调模型。
这就是 `engine/spine/`。

## 3. 分层图

```
        ┌──────────────────────────────────────────────────────────┐
        │  viewer/          浏览器界面（不参与任何判定）             │
        └───────────────────────────┬──────────────────────────────┘
                                    │ HTTP / JSON
        ┌───────────────────────────▼──────────────────────────────┐
        │  engine/api/      路由、鉴权、静态资源                    │
        │                   ── 只做"转发"，不含业务判断             │
        └───────────────────────────┬──────────────────────────────┘
                                    │ 函数调用
        ┌───────────────────────────▼──────────────────────────────┐
        │  engine/graph/    案件层：持久化 + 编排                   │
        │                   cases.py / validation.py                │
        └───────────────────────────┬──────────────────────────────┘
                                    │ 组装输入 / 存结果
        ┌───────────────────────────▼──────────────────────────────┐
        │  engine/spine/    ★ 纯核心：无数据库、无时钟、无模型      │
        │                   ir.py / verify.py / gate.py / bundle.py │
        │                   profiles/  ← 场景在这里插进来            │
        └───────────────────────────▲──────────────────────────────┘
                                    │ 产出主张/证据
        ┌───────────────────────────┴──────────────────────────────┐
        │  engine/intake/   原始输入 → 文本（音频、文档）           │
        │  engine/extract/  文本 → 带归属的片段 / 主张              │
        │  engine/orchestrator/  把上面两步接成一条流水线           │
        └──────────────────────────────────────────────────────────┘

        横切：engine/storage/（SQLite）· engine/guardrails/（审计、备份、隐私）
```

**依赖方向永远向下。** `spine` 不知道 `graph` 存在，`graph` 不知道 `api` 存在。
任何反向引用都是架构违规。

## 4. 六层各自的职责与边界

### 4.1 `engine/spine/` — 证据脊柱（纯核心）

**职责**：定义"证据"是什么，并据此判定。

| 文件 | 负责 |
| --- | --- |
| `ir.py` | 中间表示：`Artifact` `EvidenceRef` `Claim` `Finding` `Approval` `TrailSnapshot` `Case` |
| `verify.py` | 引用核验：一段引文**真的**出现在原文里吗（逐字比对，确定性） |
| `gate.py` | 非补偿闸门：多条硬条件，任一失败即不放行 |
| `bundle.py` | 证据包：把所有东西打包成离线可复核的 zip + 校验脚本 |
| `profiles/` | 场景配置：必需材料、闸门条款、维度、签署角色 |

**这一层必须保持纯粹**，因为它承载的是"可复现"这个承诺。判断它有没有越界的
标准很简单：**如果给它换一台机器、换一个时区、断网运行，结论是否完全一样？**
只要引入数据库、时钟、随机数或模型调用，答案就会变成"不一定"。

关键实现约束：

- 闸门结论的 hash 只覆盖**封闭字段集** `CORE_KEYS = (verdict, clauses, caveats,
  blocking, issuable)`，且条款内只覆盖 `CLAUSE_CORE_KEYS`。
  界面要加 `requirement`、`stale` 这类展示字段时，必须落在集合外——
  否则"加了一个给人看的字段"就等于"结论被篡改"。
- 时间戳 `evaluated_at` **不进 hash**。同一份证据在不同时间求值，结论必须等价。

### 4.2 `engine/graph/` — 案件层

**职责**：把 spine 的纯函数接到真实世界——存起来、读出来、跑一遍。

- `cases.py`：案件的增删改查、材料入库、签署、跑闸门、导出证据包。
- `validation.py`：8 项自检（`CHAIN-01` … `EVIDENCE-01`），产出"黄金线索"报告。

这一层是**唯一**知道"数据库"和"当前时间"的地方。

关于"结论过期"的设计要点：案件维护两个单调递增的计数器 `revision` 和
`gate_revision`。求值闸门时把 `gate_revision` 记成当时的 `revision`；之后任何
改动都会推高 `revision`，结论自动判为过期，导出被拒。

> 为什么不用时间戳比较？时间戳只精确到秒。同一秒内"求值完又改材料"时，
> `updated_at == evaluated_at`，严格大于比不出来，过期结论会被当成有效的导出去。
> 这不只是理论问题——它就发生在测试里。

### 4.3 `engine/intake/` — 原始输入层

**职责**：把人类世界的东西变成文本。音频转写、文档解析、静态加密、注入防护。

这一层不产生任何判断，只负责"拿到字"。失败要**明确报错**，不能返回空字符串
让下游把"没读到"当成"没有内容"。

### 4.4 `engine/extract/` — 抽取层

**职责**：从文本里取出**带归属**的内容。

- `diarization.py`：谁说的（面试官 / 候选人 …）
- `interview_analysis.py`：问答配对（问了有没有答、答没答到点上）
- `extract_claims.py`：把句子变成待核验的主张
- `identity.py` / `jd_struct.py`：身份消歧、岗位要求结构化

"带归属"是关键：没有归属的文本无法追责，而追责正是这个系统存在的理由。

### 4.5 `engine/orchestrator/` — 编排层

**职责**：把 intake 和 extract 接成一条流水线，并对外发事件。

- `ingest.py`：文件夹 → 案件（自动猜材料角色，再映射到 profile 契约）
- `events.py`：事件总线
- `context.py` / `agents.py` / `runs.py`：人才筛选场景的评审执行（历史模块，仍在用）
- `rubric.py`：评分标准版本化

一个重要约定：`ingest` 猜出来的材料角色如果和 profile 要求的不一致，
**以 profile 为准**做映射，并把映射结果记进 `warnings`。
不静默丢材料，也不静默改结论。

### 4.6 `engine/api/` — 接入层

**职责**：HTTP 路由、鉴权、静态资源。**不含业务判断。**

路由函数应当短到能一眼看完：取参数 → 调 graph → 返回 JSON。
如果某个路由里出现了 `if 金额 > ...` 这样的判断，那它放错层了。

### 4.7 横切：`engine/storage/` 与 `engine/guardrails/`

- `storage/`：SQLite 连接、schema、迁移（当前 `SCHEMA_VERSION = 10`）。
- `guardrails/`：审计日志（哈希链、只追加）、备份恢复、隐私生命周期、回测对齐。

## 5. 一次完整判定走的路

```
用户上传材料
   │
   ▼  api  →  graph.cases.add_artifact  →  intake（解析/解密）→ storage
主张入库
   │
   ▼  api  →  graph.cases.set_claims
求值闸门
   │
   ▼  graph.cases.run_gate
        ├─ 从 storage 读出材料/主张/发现/签署
        ├─ 组装 spine 的 IR（此时才接触具体数据）
        ├─ spine.verify  逐字核验每条引用
        ├─ spine.gate    按 profile 的条款判定（纯函数）
        ├─ 记 hash（只覆盖 CORE_KEYS）
        └─ 回写 gate_json + evidence_digest + gate_revision
签署
   │
   ▼  graph.cases.sign  → revision+1（结论随之过期，需重算）
导出证据包
   │
   ▼  graph.cases.bundle_bytes
        ├─ 检查 revision == gate_revision（否则 409）
        └─ spine.bundle 打包 + 附带 verify.py
```

## 6. 三条不可协商的不变量

这三条是系统的立身之本。改动任何代码前，先确认没破坏它们。

### 6.1 非补偿（non-compensating）

闸门条款之间**不能互相抵消**。材料不齐就是不放行，不会因为"其他项很好"而
放行。这在 `gate.py` 里体现为：`verdict = fail` 只要有一个 `severity="block"`
的条款失败，不看其他条款。

> 为什么：补偿制会让"整体看起来还行"掩盖"某条硬条件根本没满足"。
> 财务、合规、招聘的场景里，这种掩盖的代价由别人承担。

### 6.2 结论必须对应当前证据

材料变了，旧结论立即失效。见 §4.2 的 `revision` / `gate_revision`。

### 6.3 不确定的地方要显式暴露

系统宁可说"不知道"，也不假装知道。具体表现：

- 未外部锚定的审计链报 `warn`，不报 `pass`，并写明"库内可核验，不等于不可篡改"
- 材料角色被映射时报 `warnings`
- 结论过期时报 `stale: true`
- 材料被截断时保留头尾并插入 `…（中段已省略）`，且记录 `truncated_sections`

## 7. 怎么加一个新场景

**不要改 spine。** 正确做法是在 `engine/spine/profiles/` 下新建一个文件：

```python
from engine.spine.profiles.base import Profile
from engine.spine.gate import standard_clauses

def build():
    return Profile(
        key="contract",
        version="2026.1.1",
        label="contract@2026.1.1",
        required_roles=["contract", "amendment", "signature"],
        clauses=standard_clauses(),        # 或自定义条款
        judge_roles=["maker", "checker"],
        dimensions=["主体适格", "条款完备", "签署有效"],
    )
```

然后在 `profiles/__init__.py` 里 `registry.register(build())`。

`GET /api/profiles` 会自动列出它，前端不需要改代码。
**这就是"领域无关"的实际含义**：新场景是配置，不是分支。

## 8. 已知边界（诚实说明）

- **未做外部锚定**：审计链的哈希链只在库内自洽，没有接外部时间戳/签名服务。
  所以它能证明"没被偷偷改过"，但不能证明"某个时间点之前就存在"。
  系统在结论里如实标为 `warn`。
- **人才筛选场景的遗留模块仍在**：`agents.py`、`runs.py`、`store.py`、
  `guardrails/align.py` 等来自上一代架构，仍在为 `profile: talent` 服务。
  它们与新分层共存，但不在证据链的主路径上。
- **`engine/` 根目录有历史脚本**：`do_restructure.py`、`fix_imports.py`
  是一次性重构脚本，不属于运行时代码。
